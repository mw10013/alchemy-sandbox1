### 1.1 What legacy does

**Storage (D1, `src/lib/Repository.ts`).** One `Repository` service over two D1 clients (`D1Session` for replica reads, `D1Primary` for writes and read-your-writes). The member and team methods:

| Method                 | Does                                                                                                                                                                                                                                                                                  |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `listMembersPage`      | Keyset page by email (`email > coalesce(after, '')`, `limit + 1`), each row with `teamCount` (correlated subquery), `q` matched anywhere in the email ignoring case, `matches` counted over every page when searching. `PageInput` / `Page` / `toPage` are the shared paging shape.   |
| `addMember`            | Idempotent for the row; the ceiling (`membersAtCeiling(countMembers)`) applies to a new email only, so re-adding an existing member at or over the ceiling succeeds. Count-then-insert, two statements; the race (two adds at the ceiling) is accepted in the JSDoc. Returns the row. |
| `deleteMember`         | `delete … returning id`; none is `MemberNotFoundError`. Returns the id for the revoke. Better Auth sessions are not deleted; the gate refuses them next time.                                                                                                                         |
| `findMemberDetail`     | The member, one page of their teams by name, the count of all their teams, and the shop's teams they are not on (the Add to teams dialog's candidates).                                                                                                                               |
| `addMemberTeams`       | Member checked up front (`MemberNotFoundError`), then one D1 batch of `insert or ignore … select … from Team t join Member m on m.shop = t.shop`: a team of another shop matches no row and is dropped.                                                                               |
| `listTeamsPage`        | As `listMembersPage`, by name, with `memberCount`; search ignores case on both sides.                                                                                                                                                                                                 |
| `createTeam`           | `countTeams >= ShopLimits.maxTeams` is `TeamLimitError`; `insert or ignore … returning`: no row is `TeamNameTakenError` (no reliance on D1's constraint text). Exact-name uniqueness: "Cutters" and "cutters" are two teams.                                                          |
| `renameTeam`           | `update or ignore … returning id`; on no row, one query tells `TeamNameTakenError` from `TeamNotFoundError`.                                                                                                                                                                          |
| `deleteTeam`           | Reads the team's member ids **before** the delete (the edges cascade with it), deletes, returns the ids for the revoke; none deleted is `TeamNotFoundError`.                                                                                                                          |
| `findTeamDetail`       | The team, one page of its members by email, the count, and the shop's members not on it (candidates).                                                                                                                                                                                 |
| `setTeamMember`        | Remove: unconditional, scoped through `Member.shop`, cannot fail. Add: insert-select across the shop join, `on conflict do nothing`; no row and no existing edge is `TeamNotFoundError`.                                                                                              |
| `addTeamMembers`       | The batch mirror of `addMemberTeams` from the team side.                                                                                                                                                                                                                              |
| `findMemberAccess`     | The gate's one query: membership plus teams by left joins, so a teamless member is `teams: []`, a deleted one `none`.                                                                                                                                                                 |
| `listMemberShops`      | The sign-in gate and Your stores. Here: `Members.listShopsOf`, done.                                                                                                                                                                                                                  |
| `teamWithMemberExists` | The D1 half of the home page's setup guide (`SetupFacts`).                                                                                                                                                                                                                            |
| `sweepExpiredAuth`     | Deletes up to `sweepBatch` expired `Session` and `Verification` rows on the sign-in path.                                                                                                                                                                                             |
| `keepNewestSessions`   | Keeps a user's newest `maxSessionsPerMember` sessions after a sign-in; the hook revokes the deleted sessions' sockets.                                                                                                                                                                |

Errors are `Schema.TaggedError`s: `RepositoryError` (a row that does not decode), `TeamNameTakenError`, `MemberCeilingError`, `TeamLimitError`, `TeamNotFoundError`, `MemberNotFoundError`. D1 has no interactive transaction, so every multi-row write is a `batch` and every invariant that needs a read first is a separate statement with its race named.

**The data-model table.** `D1_TABLES` (`src/lib/D1Schema.ts`) is the D1 spec: one row per structural rule with `holds by` and `pinned by`. The member and team rows: identified by shop and email, email lowercase and trimmed, at most 254 characters; a member has one shop and goes with it; deleting a member removes their edges and nothing else points at them; re-adding mints a new id; access is the row (no role, no state); matched to a user by email at sign-in only; a team is identified by its exact name in a shop, trimmed, non-empty; a team never crosses shops (`schema+app`: the write paths hold it); **a team delete goes to D1 first, then nulls every actor pointer, and the next team delete nulls pointers to any team already gone.**

**Screens** (`src/routes/app.members.*`, `app.teams.*`, `src/lib/teams.ts`). The resource-index pattern legacy's controls table names:

- **Members** (`/app/members`): a paged `s-table` (Member, Teams), search (`q`) and page (`after`) in the URL, read leniently; an Add member modal (email field with the 254-character text limit) that lands on the new member's page; an empty state; the ceiling message "A shop can have 50 members."
- **Member** (`/app/members/$memberId`): heading the email; a Teams section (paged by `teamsAfter`, each row with Remove); Add to teams modal over the candidates (search field only from `SEARCH_FROM` = 6 candidates); Details aside (Added); Delete member modal ("Delete <email>? This can't be undone."), then toast "Member deleted" and back to the index. "Member not found" page for a stale id.
- **Teams** (`/app/teams`): as Members, columns Team and Members; Create team modal (name, `TeamName`'s cap); "A team with that name already exists."
- **Team** (`/app/teams/$teamId`): Members section (paged by `membersAfter`, Remove per row), Add members modal, Rename modal, Delete modal, Details aside.
- `INDEX_PAGE_SIZE` 25, `DETAILS_PAGE_SIZE` 10. `teams.ts` holds the shared copy (`NAME_TAKEN`, `TEAM_GONE`, `DELETE_CONFIRM`, `DELETED_TOAST`) and `failWith`, which turns a tagged failure into merchant copy before the server-function seam.
- Every write is a server function with `shopifyServerFnMiddleware`; the page then calls `router.invalidate`. **Except team delete**, which is the `ShopAgent.deleteTeam` callable over the merchant socket (§1.3).

**Revocation.** Identity on a socket is a connect-time snapshot (`memberId`, `teamIds`), so every edit that changes a member's teams or membership calls `ShopAgentClient.revokeMemberConnections(shop, {memberIds})` after the D1 write: remove from team, add to teams, add members, delete member. The actor closes those members' sockets with 3401; each reconnects through the gate with what now holds. Best effort: a failed close is logged, the edit stands. Not after add member (no sockets yet) or rename (sockets carry ids, not names).

**Team delete in the actor** (`agent/ShopWork.ts` `deleteTeam`). Because the object's SQLite holds `teamId` pointers (workflow tasks, run tasks) that no foreign key reaches, legacy ran team delete inside the actor: `Repository.deleteTeam` (D1), then `WorkflowRepository.unassignTeam` for this team and for any team id still in use but gone from D1 (the repair), then `reconcileAllNow`, then close the team's members' sockets, then publish. `NotFound` still nulls and publishes.

**Member area** (`shop.tsx`, `shop.index.tsx`, `MemberAccess.ts`). `/shop` ("Your stores") lists the member's shops, or "You don't have access to any shops yet. Ask the merchant to add your email on their Members page.", and a Sign out. `requireMember` asserts membership (404 to a stranger), then the plan (lapsed redirect; slice G).

### 1.3 What must change for Alchemy and Effect

1. **`Members` in the actor (Q0).** Legacy's object built `Repository` over `env.D1` in its own runtime (`makeRunEffect` in `ShopAgent.ts`) and used it for the shop's live teams (`teams()` in `agent/ShopWork.ts`, about ten sites from E on), `deleteTeam`, and token refresh. The actor already yields `ShopSessions` over `AuthDb` (the correction); it now yields `Members` the same way, the Backend's own layer. Every member and team write then runs in the actor, which closes the affected members' sockets itself, by tag, with no stub round trip. A D1 call from inside the actor opens the input gate, so other calls can interleave while it waits; legacy accepted this for `deleteTeam`, and the order "D1 first, then null every pointer; the next delete repairs" is what makes E's half safe.
2. **Each callable sorted** (roadmap Q5 as tightened by §0.1 A2). First-render reads stay server functions → Backend → `Members`, reading D1 in the Backend as legacy's loaders read it in the Worker, without waking the actor; each takes the merchant's session token (verified, not exchanged, as `BackendApi.listOrders`) and refuses a shop with no `ShopSession` (`ShopNotInstalled`). Every write is a merchant procedure on the `/app` layout's socket (Q17); after it answers, the page calls `router.invalidate`, as legacy's did after its server function (Q18). No read is live, so no procedure reads members or teams and no write sends a notice (Q18).

### 1.4 Risks

- **`s-app-nav` and the guards.** If App Bridge's nav navigates the frame without the search the `/app` guards need, each nav click is a session-token bounce (a visible reload). Verify on the dev store before building on it.
- **D1 unit tests.** The `Members` code runs on `@effect/sql-d1`, whose `batch` the Node SQLite client lacks. Q4's adapter may not cover what D1 does (foreign keys on by default, `returning` with `or ignore`). The first step proves it or falls back.
- **Count-then-insert races** on the ceilings stay, as legacy accepted. A merchant double-submitting Add member at 49 can reach 51.
- **Revoke after a partial batch.** A batch is atomic; the revoke runs after it, best effort. No change from legacy, except that the close now runs in the same actor call as the write.
- **Interleaving in the actor.** A procedure's D1 call opens the actor's input gate, so a second press (or a webhook) runs meanwhile. The writes are each one statement or one batch, as legacy's were in the Worker, so nothing new can tear; the ceiling's count-then-insert race is the one above.
- **e2e ceilings.** Specs add members and teams to the one e2e store in parallel; the fixture is reloaded each run, so 50 is far, but a spec must never count rows (testing research Q3).

## 5. Questions and recommendations

0. **Does the actor get D1?** Legacy's object had `env.D1` and used it for teams, team delete and token refresh. **Decision (review, 2026-10-17):** yes, read and write, through the same `Members` service the Backend uses. **Revised for §0.1 A1:** the decision's "Shopify calls and token refresh stay in the Backend" is superseded; the actor already refreshes and makes the one-order Admin calls. The actor yields `Members` in its outer phase beside `ShopSessions`, over the Backend's own layer; the Backend keeps `Members` for the loaders, the gate, the sign-in check and the fixture.
1. **How does team delete land?** Legacy: a merchant socket callable, because the object held D1 and nulled its own pointers in the same call. **Recommendation (revised for §0.1 A2):** the `MerchantDeleteTeam({ teamId })` procedure, as legacy: the actor deletes in D1 through `Members` (edges read before the delete), closes the team's members' sockets with 3401, logs, and answers `DeleteTeamResult` (`NotFound` for an unknown id, as data). The page then shows the toast and navigates to `/app/teams`, as legacy's.
2. **The actor's half of team delete (null task pointers, repair, reconcile).** Nothing in the actor points at a team until E. **Recommendation:** E adds it inside `MerchantDeleteTeam`, after the D1 delete, as legacy's `deleteTeam` does, reading live teams from D1 for the repair, and sends E's notices; the handler's JSDoc names the seam until then.
3. **One `Members` service, or `Members` plus `Teams`?** **Recommendation:** one, as legacy's one `Repository`: the team writes read and write `Member` rows (edges, candidates, counts), and the fixture's batches already span both. Port the methods with legacy's names (`addMember`, `deleteMember`, `createTeam`, …), retire `add`, `remove`, `find` and `teamIdsOf` where `addMember`, `deleteMember` and `findMemberAccess` replace them, and rewrite the SQL lowercase. The gate uses `findMemberAccess`.
4. **Where do the D1 repository tests run?** Legacy ran them on real D1 in workerd. The domain spike put the actor's repositories in unit over `@effect/sql-sqlite-node`; `Members` is different because it runs on `@effect/sql-d1`'s `D1Client` and uses `sql.batch`. **Recommendation:** unit, by giving `D1Client.layer` a small test adapter that implements the `D1Database` binding (`prepare`, `bind`, `all`, `raw`, `run`, `first`, `batch` in a transaction) over `node:sqlite` with `pragma foreign_keys = on`, migrated from `migrations/0001_init.sql`. Production code is unchanged and the real `Members` runs. The plan's first step proves it on three cases (a batch, a cascade, `insert or ignore … returning`); if it fails, the repository tests go to integ through one `IntegRpcs` procedure per method family, which is slower.
5. **Where does `membersAtCeiling` go?** It is in legacy `domain/Billing.ts`, slice G, but the ceiling is plan-independent and needed now. **Recommendation:** create `src/domain/billing.ts` with `membersAtCeiling` alone, its JSDoc and its legacy test; the import-direction lint already has a `billing.ts` override. G ports the rest of the file around it.
6. **"Seat count": what ships in C?** **Recommendation:** the ceiling only (50 members, 50 teams, the refusals and their copy). Seat events, the seat mark, the "billed" tile and the included-seats copy are G.
7. **Paging and search on the four screens.** The orders slice shipped one page and it became an open issue. **Recommendation:** port legacy's keyset paging and search whole: `q` and `after` in the URL with lenient decoding, `matches` when searching, 25 per index page and 10 per details page, `useNextPageEntry` for Previous.
8. **Screen parts.** **Recommendation:** port on demand (legacy-port Q11) the parts these four pages use and this repo lacks, with legacy's names and their rows of `Screen.ts`'s parts table: `FilterRow`, `ListSearchField`, `SearchLine`, `TextLimit`, `Token`, `Pairs`, `TableFrame`, `End`, plus the `LocalDateTime` component. Their helpers come with them: `searchParams.ts` (`lenientSearchKey`, `ListSearchParam`), `tablePages.ts`, `form.ts` (`fieldError`, `mutationErrorMessage`) and `teams.ts`'s copy.
9. **The App nav.** **Recommendation:** add `s-app-nav` to the `/app` layout now with Home (`rel="home"`), Orders, Teams and Members, as legacy's (Workflows joins with E), rendered only once hydrated for legacy's reason (§1.0), and keep the App Home's links. Verify first, on the dev store, that a nav click keeps the `/app` guards' search; if it bounces, the nav links carry the search the way the App Home's link does, and record it. `test/e2e/embedded/socket.spec.ts` then navigates Orders → App Home by the nav's Home link instead of `window.__TSR_ROUTER__` (the correction's open item); if the hoisted nav is not reachable from Playwright, by the App Home link from a page that has a `BackLink` to it, and record which.
10. **`SocketBanner` on these pages.** **Recommendation (revised for §0.1 A3):** nothing to add. These pages sit under the `/app` layout, whose `ShopSocket` holds the tab's socket and renders `SocketBanner` above every page (the correction's Q11). A write pressed while the socket is lost fails, and the page shows the orders screen's lost-socket copy through the same `thrownCopy`, legacy's "Still connecting" case.
11. **The member area in this slice.** **Recommendation:** `/shop` takes legacy's "Your stores" copy, empty state and Sign out; its links stay on `/shop/$key`, whose counter page stays until F replaces it with the work list. No other member-area change.
12. **Session cap and auth sweep.** Legacy keeps a user's newest `maxSessionsPerMember` sessions (revoking the rest's sockets) and sweeps expired `Session` and `Verification` rows on sign-in. Neither is here. They are `Repository.ts`'s last D1 methods outside plans and the console. **Recommendation:** port both in this slice (sub-slice 6), with the `D1_TABLES` rows that state them and the legacy test. `session.delete.after` revokes a session Better Auth deletes, but `keepNewestSessions` deletes by SQL, which fires no hook, so it answers the deleted ids and the hook revokes each one (`ShopActors.revoke(shop, "session", id)` on each of the user's shops).
13. **`D1_TABLES`.** **Recommendation:** port it as legacy has it: an exported `D1_TABLES` (and `BETTER_AUTH_TABLES`) in `src/backend/` with the whole rules table as its JSDoc, including the shop rows and the G and H rows whose pinned tests arrive later; the "migrations create exactly" test pins the names. The SQL comments in `0001_init.sql` stay and point at nothing.
14. **The admin's `/admin/members` page.** It lists every shop's members for the operator; legacy had no such page. **Recommendation:** leave it as it is; the console is H.
15. **The setup guide and `teamWithMemberExists`.** **Recommendation:** both with E, where the guide's second fact (a workflow) exists. Porting the read now would leave a method with no caller.
16. **Where does it run?** Nothing else is in flight; E waits for C. **Recommendation:** one implementation thread on `main`. `wt-01` stays idle.

17. **Member and team writes as procedures, where legacy used server functions.** Legacy wrote D1-only edits from POST server functions in the Worker and then called `revokeMemberConnections` on the object's stub; only team delete went to the object, over the socket. §0.1 A2 makes every browser write a procedure, and a server function writes only when the actor cannot do the work; with `Members` in the actor (Q0) it can. **Recommendation:** the eight `Merchant…` procedures of §1.3. Each validates its payload with the domain schemas (`Email`, `MemberId`, `TeamId`, `TeamName`), writes through `Members`, and closes the members §1.3 names locally. What this buys: one transport for writes, the revoke without a second round trip, and E's team pointers already in reach for every team edit. What it costs: each write wakes the actor, which legacy's did not (it woke the object for the revoke anyway, on every edit but add and rename).
18. **How a page refreshes after a write, and whether these reads go live.** Legacy re-ran the loader (`router.invalidate({ sync: true })`) after each write; no member or team read was live, and nothing published. **Recommendation:** keep legacy's: the page awaits the procedure's answer, then `router.invalidate`; no `Merchant…` read procedure, no reactivity key, no notice. A second merchant tab sees an edit on its next navigation, as in legacy. E adds a teams key if its editor's team picker has to stay live.
19. **Where the procedure handlers live.** **Recommendation:** a plain constructor `makeMembersAgent({ members, revoke, shop })` in `src/backend/shop-actor/members-agent.ts` (`MembersAgent`, after `OrdersAgent` and legacy's `agent/` modules), built once per activation; the actor's `MerchantRpcs` handlers call it. Its unit tests run over `Members` on the unit D1 layer (Q4) with a recording `revoke`, and integ covers the socket and the role refusal.
