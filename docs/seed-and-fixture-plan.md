# Seed and fixture: implementation plan

This plan implements `docs/seed-and-fixture-research.md`. Read that first: its §1 and §6 hold the settled decisions, and this plan does not re-argue them. Legacy paths are relative to `refs/baton-legacy/`.

**Rules for the implementer:**

- Follow `AGENTS.md`: Vite+ only, Effect Schema for all decoding, `Match`, `Schema.TaggedError`, `Effect.fn`, and the JSDoc rules.
- Code comments never cite this plan or the research, nor their section or question labels.
- Do not commit. Leave the work uncommitted on `main`.
- Record every deviation from this plan, and every issue found, in §4 as you go, not at the end.

---

## 0. Outcome

1. **The seed.**
   - The `Seed` Action writes only the admin user: `a@a.com` in dev, and `support@mw10013.com` in staging.
   - `seed/test.sql` is unchanged. It keeps the integration tests' fake shops and members.
   - The production environment does not exist yet. When it lands, its seed file is the `support@mw10013.com` row, and the exhaustive `seedFileFor` forces that choice.
2. **The fixture.** One RPC endpoint, `/api/dev/fixture`, replaces one installed shop's data with a `ShopFixture`.
   - It replaces the shop's members, teams and team memberships in D1.
   - It replaces the shop's actor workflows and orders.
   - It is served only on dev, test and e2e stages.
3. **`vp run fixture`.** One command that, in parallel:
   - writes the fixture's store half (products and the 3 real orders) into this checkout's `SHOPIFY_DEV_STORE` through Shopify CLI;
   - calls the endpoint for that shop.

   `stores:seed` goes away. `stores:check` stays.

4. **The data.** Legacy's showcase data is ported in full as the dev fixture, `fixture.ts`. That includes the run progress (`progress` and `after`), which is decoded but not yet applied: there are no runs until reconcile is ported.
5. **Words.** "Operator" becomes "admin" everywhere, and Shopify's admin is always written "Shopify admin".
6. **The member side.** `/shop` lists the signed-in member's real shops instead of linking to `SEED_SHOP`.

**Out of scope:**

- Runs and run tasks.
- Order sync, webhooks and bulk sync.
- Moving e2e onto its real store.
- The production environment.
- Staging store writes. The staging store keeps what it has.

## 1. Design details the research left to the plan

**1.1 The endpoint is one RPC, not a bespoke HTTP route.**

- The repo's Backend surface for scripts and tests is RPC: `TestControlRpcs` is served with `RpcServer.toHttpEffect` in `src/backend/worker.ts`, and the Website forwards it through `rejectRequest`.
- So the endpoint is `FixtureRpcs`, with one procedure, `LoadFixture({ shop, fixture })`, served at `/api/dev/fixture`.
- The research's HTTP statuses map as follows:

  | Research status                    | Here                                                                       |
  | ---------------------------------- | -------------------------------------------------------------------------- |
  | 404 (not a dev, test or e2e stage) | 404 for the whole path: the server is not mounted or is refused before RPC |
  | 409 (no `ShopSession`)             | `Schema.TaggedError` `ShopNotInstalled { shop }`                           |
  | 400 (bad body)                     | The RPC decode failure                                                     |
  | 200                                | `{ members, teams, workflows, orders, lineItems }` counts                  |

- Record this mapping in §4 as a deliberate deviation.

**1.2 Where it is available.**

- Mount it on `dev`, `test` and `e2e`. `staging` never mounts it.
- The research said dev and e2e only. `test` is added because the integration tests deploy the `test` environment and must exercise `LoadFixture` against a real actor. `test` is per-developer and local, with no tunnel, so it carries the same risk as e2e. Record this in §4.
- Wire it the way `ShopifyFake` and `TestControl` are wired: a binding chosen by `Match` on the environment in `wireBackend` (`src/backend/stack.ts`). The Worker serves the route only when the binding is present.

**1.3 No localhost guard.**

- The environment is the whole gate: the stack binds the endpoint on `dev`, `test` and `e2e` only (1.2), so a deployed stage answers 404.
- In dev, Shopify CLI's tunnel makes the local server public, so whoever has the tunnel URL can reach the endpoint. That is accepted: the same person can already sign in as the admin, because dev hands magic links back inline. Exposure through the tunnel is a property of the whole dev stage, not of this endpoint.
- The user settled this after plan review, replacing the research's "environment plus localhost". A hostname check was forgeable (Alchemy's Vite dev proxy builds the URL from `X-Forwarded-Host`), and hardening it bought nothing while sign-in stays open.

**1.4 The data shapes.**

- `src/contract/fixture.ts` holds the Effect Schemas for `ShopFixture`. They are shared by the script, the Website route and the Backend. Port the shapes from legacy `e2e/seed.ts` (`SeedMember`, `SeedTeam`, `SeedWorkflow`, `SeedWorkflowTask`, `SeedProgress`, `SeedOrderChange`, `SeedLineItem`, `SeedOrder`) and from `seed/dev-shop.ts` (`Product`, `Variant`, the store `Order`, `OrderLine`). Legacy already has Effect Schemas for most of these: `SeedWorkflowTask`, `SeedProgress` (with its `doneAndAdvanceExclusive` filter), `SeedOrderChange`, `SeedPlacedDaysAgo` and `SeedOrdersInput` in legacy `src/lib/domain/ShopWork.ts`, and `DevSeedInput` in legacy `src/routes/api.dev.seed.ts`. Start from those, not from the `e2e/seed.ts` interfaces.
- Shape details the legacy types carry and the port must keep:
  - `FixtureProgress`: `done`, `advance`, `started`, `blocked` (reason), `byMerchant`, `by` (email), `note`, `cancelled`; `done` and `advance` are exclusive.
  - `FixtureOrder` carries the progress keys too, minus `note` (the order's `note` is the order note). They apply to every item on the order that has no `progress` of its own.
  - A line item's `properties` is an array of `{ key, value }` with `value: string | null`, defaulting to `[]`.
  - `FixtureOrderChange.lineItems` is `[{ position, currentQuantity? }]`, positions 1-based.
  - A workflow task's `step` and `instructions` are optional; a workflow's `state` is optional (see 1.5's default).
- `ShopFixture` contains:
  - `products`, the store half;
  - `storeOrders`, the store half: the 3 real orders;
  - `members`: emails, decoded through the existing `EmailFromInput` or `Email` from `src/contract/auth.ts`;
  - `teams`, `workflows` and `orders`: the D1 and actor half.
- `LoadFixture`'s payload carries only the D1 and actor half, `ShopFixture` minus the store fields. The script sends only that half.
- Validation belongs in the schemas, not in code:
  - non-empty trimmed names;
  - unique team names, unique workflow names and tags;
  - every team member is a fixture member;
  - every task's team is a fixture team or `null`;
  - every `by` is a member, on an order's progress keys and on an item's `progress`;
  - every item `workflow` names a fixture workflow;
  - legacy `replaceWorkflows`' own refusals: steps are dense from 1 and non-decreasing (draft tasks included), and a workflow whose `state` is `active` has at least one task and every task has a team. Legacy's `maxWorkflows` and `maxTasks` limits are not ported: Baton has no such limits yet.

  Use `Schema` checks on the struct. Where a cross-field check is too awkward as a schema, record that in §4 rather than hand-rolling it silently.

**1.5 Rows the Backend derives.** These are pure functions in `src/backend/fixture.ts`, unit-tested.

- **Ids** are new each load, minted the way `Members.add` mints them. Replace means nothing has to survive a reload. Fixture order ids are the exception: they are deterministic and always carry the `fixture-` prefix.
- **Team ids** are minted for D1 first. Workflow task `teamId`s are filled from the name-to-id map.
- **Workflow row:**
  - `id`: `crypto.randomUUID()`.
  - `name`, `tag`.
  - `state`: the fixture's state if given. Otherwise `active` if the workflow has tasks and every task has a team, else `inactive`. This is legacy's default, from `WorkflowRepository.replaceWorkflows` and the seed defaults.
  - `updatedAt`: now.
  - `tasks`: JSON of `{ id, position, step, name, teamId, instructions }`. Positions run 1 upward. A task with no `step` gets the previous task's step plus 1, and the first task gets 1. Confirm the JSON shape against legacy `src/lib/domain` (the workflow task type) and the actor's `Workflow` CHECKs in `src/backend/shop-actor.ts`.
  - `draftTasks`: the draft's tasks in the same shape, or `null`.
- **Order row**, following legacy `ShopWork.seedOrders`:
  - `id`: `gid://shopify/Order/fixture-<n>`. `legacyId`: `fixture-<n>`. `name`: `#<n>`.
  - `processedAt`: `now − placedDaysAgo·86_400_000 + index`, `index` 0-based over the whole order list, so orders placed the same day still sort by number. `placedDaysAgo` is part of each fixture order, computed in `fixture.ts` exactly as legacy `e2e/showcaseFixture.ts` does: `Math.floor(((orders.length − 1 − i) · 10) / (orders.length − 1))` for the order at index `i`, so #1201 is 10 days old and #1242 is today. Legacy's `SeedPlacedDaysAgo` schema bounds it.
  - `updatedAt`: now. `cancelledAt`: `null`.
  - `fulfillmentStatus`: the fixture's, or `"UNFULFILLED"`. `fullyPaid`: `!unpaid`. `note`.
  - `syncedAt`: now. `countedAt`: `0`, so usage never counts it.
- **`after` is applied to the stored row now**, so the orders read as closed or changed:
  - `cancelled` sets `cancelledAt` to now;
  - `fulfillmentStatus` replaces the status;
  - a line item's `currentQuantity` replaces that item's.

  `progress`, an order's own progress keys and an item's `workflow` choice are decoded and ignored: each acts on a run, and there are no runs until reconcile is ported. So until then the fixture shows no run states (making, blocked, done), and `after` closes no runs.

- **Line item row:**
  - `id`: `<orderId>/line-<position>`, with positions starting at 1.
  - `orderId`, `title`, `variantTitle` or `null`, `sku` or `null`, `quantity`.
  - `currentQuantity`: the item's own, or else `quantity`; then `after`'s, if it has one.
  - `productTags`: JSON. `properties`: JSON of `{key, value}`.
- Name the id prefix once as an exported constant, with a JSDoc saying fixture orders are never in Shopify and must never be synced.
- **Statement size.** D1 and Durable Object SQLite both allow at most 100 bound parameters per statement. A multi-row `INSERT` of 42 orders (11 columns) breaks that, so insert row by row, or in chunks under the limit.

**1.6 What one `LoadFixture` call does.**

1. `ShopSessions.find(shop)`. If there is none, fail with `ShopNotInstalled`.
2. **D1, in one batch, so it is atomic**, through a new `Members.replaceShop(shop, rows)` that answers the prior member ids:
   1. `SELECT id FROM Member WHERE shop = ?` as the batch's first statement, for the prior ids.
   2. `DELETE FROM Team WHERE shop = ?`, then `DELETE FROM Member WHERE shop = ?`. `TeamMember` cascades.
   3. Insert the fixture's members, teams and team members, one row per statement (the 100-parameter limit, 1.5).
   4. `SQL.D1` (`alchemy/SQL/D1`) returns `@effect/sql-d1`'s `D1Client`, whose `sql.batch([...statements])` runs one atomic D1 batch and answers each statement's rows in order. `withTransaction` is not supported on D1 and dies, so never use it there.
   5. The write lives on `Members`, not in `Fixtures`, because `Members` already owns the shop's identity rows and has an in-memory `layerTest`; extend that layer with `replaceShop` (it keeps members per shop; teams only as far as a test needs). That is what lets the unit tests in step 6 run without D1.
3. **The actor**, through a new schemaless method, `loadFixture({ workflows, orders, lineItems })`. It is called through `ShopActors` (`src/backend/shop-actors.ts`), which already calls `revoke` and `snapshot` this way. Inside the actor, one transaction:
   - delete `RunTask`, `Run`, `OrderLineItem`, `ShopOrder`, `Workflow` and `UsageEvent`;
   - reset the single `SyncState` row and the single `ShopUsage` row to the values the migration inserts;
   - insert the new rows.

   It is the actor's first multi-statement write. The actor's client is built with the full `DurableObjectStorage` (`SqliteClient.layer({ storage: state.raw.storage })`), so `sql.withTransaction` is storage-backed (`storage.transaction`, rolled back on failure). Wrap it as Alchemy's `Drizzle.DurableObject` does (`node_modules/alchemy/src/Drizzle/Cloudflare.ts`): run `withTransaction(body)` with `Effect.provideService(Scheduler.Scheduler, new Scheduler.MixedScheduler("sync"))`, because the transaction closes the input gate and a timer-scheduled fiber yield inside it can then wait forever. Build the scheduler once per activation. Update the `ShopActor` JSDoc, which today says a multi-statement write "will need" this, and which lists `revoke` and `snapshot` as the Backend's only methods. Do not use `storage.deleteAll`.

4. **Revoke** every prior member id (`ShopActors.revoke(shop, "member", id)`). Every prior row is replaced, so every prior id is gone. This is best effort, as `RemoveMember` treats it today.
5. **Return the counts.**

**1.7 What it never touches:**

- the `ShopSession` row;
- any other shop's rows or actor;
- every Better Auth table.
